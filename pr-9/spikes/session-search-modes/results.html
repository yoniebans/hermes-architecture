3. SEARCH FIDELITY

What "honest" means now

The biggest qualitative change isn't speed or cost — it's that the system stops papering over weak retrieval with confident-sounding prose.

The failure mode the old version had

Confident-stale (the old failure) Summary mode laundering FTS5 misses into authoritative prose. The reader can't tell the answer is fabricated.
Correct and confident What you'd want every time. The old system could deliver this — when retrieval happened to work.

tone
Honest about gaps (the new default) Fast surfaces what it found and flags what's thin. Agent can re-search with sharper phrasing before synthesising.
Over-cautious Rare. The agent hedges even on strong retrieval — minor cost, easy to dial in via prompt.

The old default (summary-on-everything) sat on the dangerous diagonal: confident in tone, but only as honest as FTS5 happened to be on the day. The new defaults pull toward "honest about gaps" by surfacing raw snippets instead of synthesised prose by default — and giving the agent the toolkit to actively widen the search when fast results look thin.

From the smoke-test corpus. Question: "what do we know about Telepath the AI startup?" (recent telegram-platform research, ~2 sessions in the DB).

new default (fast, with explicit drill if needed)

Agent runs fast(query="Telepath"), surfaces 2 real telegram sessions with snippets, calls guided on the most substantive one to pull the raw messages, and synthesises from actual conversation: founders' names, the manifesto URL, the @telepathinc tease. If retrieval had been thin, the agent would have widened the search before synthesising.
Tool priority — memory first, external sources second

The agent now reaches for the session DB before calling gh pr list, web search, or filesystem inspection on questions about prior work. The session DB carries what was discussed and decided; external tools only show the current world state. Both matter — but memory comes first, then verification.

A real case from the smoke test: asked about the status of a feature branch, the agent first calls session_search to find the prior planning discussion, then verifies the branch state with the filesystem. The old behaviour was to skip the DB entirely and answer with just the external check — which produced a technically-correct but contextually-empty answer.

The headline: summary is the only expensive mode, and the expense isn't latency, it's the auxiliary LLM call dispatched per matched session. If you're querying a topic with 5 hits, summary mode runs Opus 5 times in parallel. Reserve it for questions that genuinely warrant synthesis — for everything else, fast is 4–6× cheaper and 3× faster.
5. BOTTOM LINE

Three takeaways, one config line

What this means in practice

  • Most questions: 4–6× cheaper, 3–4× faster than before. The system now matches mode to question shape instead of paying for synthesis on everything.
  • Deep synthesis is still available — but as an opt-in for questions that demand it, not a default for questions that don't. The expensive thing is now a deliberate choice.
  • Honesty improved more than cost. Zero hallucinations across the smoke-test set. The agent says "I see weak hits, want me to widen?" instead of papering over thin retrieval. That's a quality improvement that doesn't show up in dollar figures but materially changes whether you can trust the answer.
How to try it

Two ways, depending on how much control you want. 

# ~/.hermes/config.yaml — flip the default to fast
tools:
  session_search:
    default_mode: fast    # or "summary"

# Restart hermes, then use normally. The agent will start with fast on
# most questions and only reach for synthesis when you explicitly ask.

Or force a mode per call by naming it in the prompt: "use fast mode to find sessions about X", "summary only", "drill into the most promising hit with guided". Explicit overrides always win.
