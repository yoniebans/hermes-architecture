session_search optimisation

Investigation, findings, and light spec — 2026-05-11 — hermes-agent

We investigated session_search's end-to-end cost by profiling four real queries against a 280-session database. Summarisation dominates latency (1,299× to 6,293× over snippets) but materially improves recall quality — fast and summary answer different questions. We salvaged a community PR that introduced the dual-mode design, flipped its default to summary for backwards compatibility, and propose adding a third guided mode for anchored drill-down. This page consolidates the investigation, the data, the decision, and the spec for the remaining work.

1. Problem

session_search felt slow and unreliable

Daily-planning workflows surfaced three symptoms that compounded across sessions: searches taking 30s+, occasional empty results for queries the user knew should match, and substantive late-session content missing from summaries. The unreliability had a compounding effect — carry-over verification, drift detection, and recall checks all depend on session_search producing trustworthy results.

H1 — "summarisation is slow"

Searches taking 30+ seconds. Each call fans out up to 3 parallel auxiliary LLM calls; the slowest dominates wall time.

H2 — "100K window misses late content"

Truncation centres on the first FTS5 match; if that's in message 1 (e.g. session-title query), late-session work isn't fed to the summariser.

H3 — "exact title returns nothing"

Some queries return zero results despite a known matching session. Suspect: sqlite3.OperationalError swallowed on FTS5 query parser failure.

2. Approach

Profile against a real database, salvage prior art, propose a light extension

Recon found PR #20238 (JabberELF) already proposed a fast/summary dual-mode — the same design we'd independently arrived at. Per hermes-agent-dev conventions, we salvaged the substantive commit, validated its claims with a profile harness, and added a default-flip and new-mode design on top.

⚠️ Critical: fast and summary share the same retrieval set

Both modes return the same three sessions. The mode parameter doesn't change which sessions are surfaced — only what's done with them. Fast wraps the FTS5 snippet and ±1 message context (~3 short messages per hit). Summary fetches each surviving session's full message list, truncates each to 100k chars, and dispatches parallel auxiliary LLM calls to recap them — see §6.5 for the per-query data flow.

For Q1 in particular: FTS5 returned three cron-job sessions that discuss the PII work — not the work session itself. Summary's recap is therefore a recap of cron transcripts that talk about the work, not a recap of the work. The chain is: actual work happened → cron job summarised it into its own transcript → FTS5 matched the cron transcript → our auxiliary LLM summarised the cron transcript → the calling agent reads that summary as if it were the source.

This isn't wrong per se — the cron summaries are themselves close to the truth — but it means summary mode's polished, confident output can hide retrieval gaps. The higher-leverage fix isn't between fast and summary: it's improving FTS5 retrieval so that both modes start from the right set of sessions.

6. Decision

Three modes for optionality; default stays summary; guided is a steering surface, not a speed play

The reasoning

The original framing — fast for discovery, summary for synthesis, default to summary because users ask synthesis questions — was based on costs measured by the harness and an assumption about what summary mode delivers. The consumer replay in §6.5 with all three modes refines the picture: fast and summary share the same FTS5 retrieval set, summary launders the same retrieval into polished prose, and guided returns the literal messages around a chosen anchor.

An honest reframing of guided. Earlier framings on this page leaned on guided's sub-millisecond tool-side latency as if that meant the drill-down flow was faster than summary. It isn't. Between fast and guided, the main agent has to think — look at the fast results, pick a hit, emit the guided tool call — and that's a full reasoning turn (~15s on Opus). End-to-end on a fresh drill-down question, fast→guided is in the same 30s ballpark as summary. Guided's value isn't speed.

Guided's value is steering. (That was the original name for it, and it captures the intent better than "guided".) When the agent calls fast, the user can see what the retrieval actually returned — three sessions, with snippets and titles — and intervene before the agent commits to an answer. "Wait, that's not the one I meant — try searching for X instead." The agent course-corrects with a fresh fast call. Compare to summary: the user waits 30s for a polished prose recap and can only react to the conclusion, not the inputs. Steering trades speed for interactivity and correctness when retrieval is imperfect — which §6.5 shows it often is.

With that reframing, the modes break down as:

  • "Find the latest …" → fast (cheap, accurate metadata comparison)
  • "What did we decide about X across multiple sessions?" → summary (cross-session synthesis, single tool call)
  • "I want to look around before committing" → fast → user reacts → fast→guided (the steering flow). Same end-to-end time as summary, but the user is in the loop.

Default decision: keep summary as the entry-point default for now. Summary is the only mode that delivers a one-call recap without preconditions, and it's the safe default for "I don't know what I'm looking for; tell me what's there." Fast and guided remain explicit opt-ins for agents (or users) who want to be in the retrieval loop.

The mode parameter is optionality — agents that know the question shape can pick fast or compose fast→guided; agents that don't get summary's safe default. The highest-leverage future work isn't the default itself but improving FTS5 retrieval (Q1's anchor missed Yoni's actual work session entirely; Q4 returned nothing) — see §9. Better retrieval improves every mode equally.

6.5. Consumer simulation

What the user actually sees: replaying the agent's next turn

This section answers a different question from §4. §4 measured how long session_search takes to run (the tool-side latency where the mode choice actually changes the cost). §6.5 holds tool-side latency aside and asks: given the same JSON the live agent would receive, what answer does the model produce for the user? The replay calls the same auxiliary path session_search itself uses (auxiliary.session_search → auto → main chat model), feeding the JSON from the §4 run as the tool result. Same model, same payload, real LLM tokens.

⚠️ The mechanism: fast and summary differ in what each internally processes, not just what they emit

Both modes start with the same FTS5 hit set. After that, the paths diverge sharply:

  • Fast mode wraps each hit's snippet (~150 chars highlighted) plus ±1 message of context — typically 3 short messages per hit. For 3 sessions that's ~3.5–3.9 kB of JSON returned to the calling agent. No additional DB query, no auxiliary LLM call.
  • Summary mode takes the surviving sessions and, for each one, issues a second DB query (db.get_messages_as_conversation(session_id)) that pulls the entire session's messages. The full transcript is formatted, then truncated to 100,000 chars per session (centred on FTS5 match locations with a 25/75 recency bias). The (up to 100k-char) truncated transcripts are dispatched as parallel auxiliary LLM calls with a system prompt asking for a structured recap. Only the recap text — typically 1–4 kB per session — is returned.

So summary mode internally processes far more raw transcript than fast surfaces to the main loop, but the calling agent never sees that raw transcript — it sees a distillation. The numbers below quantify the gap.

Internal processing — summary reads ~57–62× more raw text

Summary mode's auxiliary LLM ingests ~200–230 kB of formatted transcript per query (across 3 parallel calls). Fast mode's user-visible JSON is ~3.5–3.9 kB per query.

That's where summary's 27–37 s wall time comes from: not a single big call, but three parallel calls each on ~70–100 kB of transcript, with the slowest dominating.

Truncation is real — H2 confirmed for Q2 and Q3

2 of 3 sessions in both Q2 and Q3 exceeded the 100k cap. The auxiliary's recap on those sessions is reading a window — 25% before / 75% after the first FTS5 match — not the whole transcript.

Q2's April 23 session is 397k chars, capped to 100k. Q3's April 23 session is the same. Late-session content (resolutions, decisions, status flips) is at risk of falling outside the window. Documented as future-work H2 in §9.

Main-loop context cost — summary is ~3.4× fast (not 50×)

The 200 kB stays inside session_search — the calling agent only ever sees the recap text, around 10–15 kB total per query. So the headline tool-result inflation for the main loop is bounded at ~3.4×.

The cost the calling agent does pay is wall-clock time waiting for the auxiliary LLM (27–37 s) and a more polished but second-hand recap. The volume cost is absorbed by the auxiliary path.

Why this changes the framing

Before this measurement: "fast and summary share the same FTS5 set; summary's value-add is bounded by what an LLM can wring from the same sessions." That's literally true at the FTS5-hit layer.

But after the FTS5 hits: summary's auxiliary LLM also reads ~50× more transcript than fast surfaces. That extra material can include real signal the snippet+context didn't carry — and the recap that lands in the calling agent's context is also ~3.4× richer than fast's snippet payload. So the trade-off cuts both ways:

  • Fast: the calling agent sees the raw FTS5 snippets — small, honest about what was matched, but blind to anything outside the ±1-message window.
  • Summary: the calling agent sees a distillation drawn from up to 100k chars per session — richer, but at the cost of being second-hand and vulnerable to the truncation cliff (§5).

Neither is a clean win for "what the calling agent needs to know". Guided is the third lever in this trade-off — pull the actual messages around a chosen anchor, without summarisation and without a 100k-char truncation gamble. We'll measure it once it ships.

⚠️ What §6.5 measures — and what it doesn't

The mode-vs-mode speed comparison lives in §4: session_search itself is 5–21 ms in fast mode vs 27–37 s in summary mode (1,300–6,300× speedup). That gap is what an agent pays as a function of which mode it picks.

The next-turn synthesis (the LLM call the agent makes after session_search returns) happens regardless of mode, and varies mostly with payload size and run-to-run inference noise. Earlier drafts of this page had a "next-turn latency" column that implied summary was faster than fast on Q2 (17.84 s vs 16.34 s) — that's noise on a single LLM call against an external provider, not a real property of the modes. Including it diluted the speed story without telling us anything reliable.

So §6.5 is presented as a quality / answer-shape measurement, not a speed measurement. Use §4 to compare cost; use §6.5 to compare what the user reads.

⚠️ The structural insight

Both modes work from the same FTS5 retrieval set. Summary's value-add is bounded by what an auxiliary LLM can wring from the same sessions the snippet path already saw. When retrieval gets the right sessions, both modes deliver useful answers (Q2, Q3); when retrieval misses (Q1: cron transcripts instead of the work session; Q4: 0 hits), summary's confident prose can hide the miss in a way fast's snippets do not. Polished output without uncertainty signalling is a liability when retrieval is imperfect.

This reframes the optimisation target. Mode parameter is optionality, not a ranking; the highest-leverage fix is improving retrieval (FTS5 ranking, OR-default for multi-keyword, title/recency-aware scoring, possibly semantic search) so every mode starts from the right sessions. Tracked in §9.

6.7. Interaction model

How the agent actually uses these three modes

The PR doesn't ship an "agentic loop". It ships three tool modes that compose well through the same LLM tool-calling that every other tool uses. The model's judgement plus the schema description does all the steering. This section makes that explicit, because it's been under-documented in §6 and §7.

Activation surface — one tool, one mode argument

There is exactly one registered tool: session_search. Mode is just a string argument the LLM passes. Activation is "emit the right tool_call arguments." No router, no separate tools, no special state machine.

What the agent emitsWhat runs
session_search() (no args)Recent sessions — DB browse, no FTS5, no LLM
session_search(query="X")mode=summary (default) — FTS5 + auxiliary LLM recap
session_search(query="X", mode="fast")FTS5 snippets only, no LLM
session_search(query="X", mode="summary")Same as the default
session_search(mode="guided", session_id=..., around_message_id=...)Single-anchor drill — DB-only, returns window of messages
session_search(mode="guided", anchors=[{session_id, around_message_id}, ...])Multi-anchor drill — one window per anchor, in one call

The default lives in two places: SESSION_SEARCH_SCHEMA["parameters"]["properties"]["mode"]["default"] = "summary" tells the LLM what to assume, and mode = (mode or "summary") inside session_search() normalises it server-side. Both are needed (defaults aren't always honoured by every provider).

A drill-down is four turns of the normal agent loop

"Turn-based guided search" is just standard LLM tool calling. The agent does not call fast and guided in one step — it can't, the model has to see fast's results before it can know what to anchor on. Each tool call is a separate inference turn: 

TURN 1 — user message
  "what was the final design for the PII redaction work?"

TURN 2 — agent reasons, emits tool_call
  session_search(query="pii redaction multimodal", mode="fast", limit=5)
  └─ tool returns in ~11 ms:
     5 sessions, each with snippet + context + match_message_id

TURN 3 — agent reads fast results, reasons, emits tool_call
  session_search(mode="guided", anchors=[
    {session_id: "cron_6d05d24...", around_message_id: 12793},
    {session_id: "cron_d72ae25...", around_message_id: 12824},
    {session_id: "cron_9e8bb74...", around_message_id: 13621},
  ], window=5)
  └─ tool returns in ~3 ms:
     3 windows of raw messages, anchor-flagged

TURN 4 — agent reads windows, composes final user-facing answer
  "Here's the final design — a four-pass span-manifest pipeline on
   feat/redaction-passes, replacing the standalone redactor that was
   scoped on May 1..."

Where the ~15 s end-to-end goes: the tool walls (11 ms + 3 ms) are negligible. The cost is two inference turns against the user's main model — turn 3 (reason about fast results, emit guided call) and turn 4 (compose final answer). Each is ~7–10 s on Opus. That's why "fast → think → guided" is ~15 s end-to-end, not the ~14 ms the tool walls add up to.

What the tool does NOT do

Being explicit because the spec page underspecified this and it's where most confusion lands:

  • No enforced "stop" condition. The tool doesn't limit how many times it can be called or in what order. The agent could call fast three times in a row, or call guided cold (with a session_id and message_id from anywhere — memory, a previous chat, a user message). The schema description nudges toward "one fast, one guided", but nothing enforces it.
  • No "ask for guidance" API. "Asking for guidance" is just the agent generating a user-facing turn instead of another tool call. If the model sees five fast hits and isn't sure which to drill, it writes "I see hits in A, B, and C — which is closest to what you mean?" That's a normal text response, not a tool primitive.
  • No fast → guided coupling. Guided doesn't require a prior fast call. match_message_id in fast's response is just a convenient handle; the agent can supply any valid (session_id, message_id) pair. We just expect the common path to be fast-then-guided.
  • No max-depth or recursion limit. The agent can call guided again with different anchors after the first drill if it wants to. The tool will happily serve more windows.
  • No multi-turn state. Each call is independent. There's no "in-progress search session" the tool tracks. If the agent wants to remember which sessions it's already drilled, that's the agent's job.
Two valid steering postures: agent-as-picker, user-as-picker

The same tool surface supports two interaction shapes. Same code path, different actor doing the picking:

Agent-as-picker (typical)

User asks a question. Agent picks fast (or summary). Agent reads results, decides which to drill, emits guided. User sees only the final synthesised answer.

When this is right: user wants the answer, doesn't care about the intermediate hits.

User-as-picker (steering)

User says "find the latest sessions about X, show me the hits". Agent calls fast with a wide limit. User reads the 5–10 hits in the response, tells the agent which to drill. Agent emits multi-anchor guided with the user's picks.

When this is right: retrieval is ambiguous, the user has tacit knowledge about which session matters that the model doesn't, or the user wants to verify the agent isn't hallucinating from a recap.

The schema description hints at when each is appropriate but doesn't enforce either — both compile down to the same tool calls. "Steering surface" in §6 means the second posture is supported as a first-class workflow, not that it's mandatory.

How much shape you give the agent governs guided's synthesis

Earlier framing on this page claimed guided defaulted to a transactional transcript-walk style and that asking for "briefing-style recap" would fix it. That claim was partially wrong and a live A/B run (May 13, same query, two prompts) tells a more honest story. Recording the actual finding rather than the original prediction.

Where the synthesis work lands is still real — summary pre-digests through the auxiliary LLM (server-side, briefing prose by construction), guided returns raw messages and the main agent does the synthesis from scratch. That part of the diagnosis stands. What was wrong was assuming guided's default would land at "transcript walk." On Opus, with three multi-anchor windows of mixed message types, both prompts produced briefing prose. The difference between them was finer than transcript-vs-prose.

ModeWho synthesisesWhat you can tune from user prompt
summaryAuxiliary LLM (server-side)Limited — the aux-prompt is fixed, your phrasing affects retrieval not synthesis
fastMain agent, from snippetsLimited — there's little synthesisable material; the prompt mostly shapes how the agent navigates from there
guidedMain agent, from raw messagesHigh — synthesis structure is entirely the main agent's choice, so user prompt shapes it directly

What the A/B actually surfaced (May 13, Opus, same multi-anchor drill):

  • Prompt 1 — "drill into the most promising ones with multi-anchor guided" → chronological state-walk with named stages, analyst-notes feel, action items surfaced ("§6 drift, §6.7 addendum pending, PR #20238 status"), some confabulation about PR state.
  • Prompt 2 — "…give me a briefing-style recap, not a transcript walk" → polished narrative arc with phase headings, story-shape closer ("where it stands going into today"), verbatim quote pulling from past sessions, fewer action items.
  • Both outputs were prose. Neither was the transcript-walk the original card predicted. The strong-form "guided defaults to transactional" claim is falsified for this setup.

Refined finding: the lever isn't transcript-vs-prose, it's how much structural opinion the agent invents vs how much you specify. Default = analyst notes with action items; explicit-briefing = curated executive narrative with quoted sources. Both have value, in different situations. There's no "right" default — but there IS real per-prompt steering room on guided that you don't have on summary.

Schema-tuning candidates worth A/B'ing next: verbatim quote-pulling cue (does asking reinforce it or backfire?), action-item surfacing under briefing posture (Prompt 2 lost that — can a single additional line restore it without breaking the narrative shape?), and honest-about-gaps cue ("flag explicitly when fewer than N sessions found, or when retrieval feels meta-only"). None of these need code changes; they need iterating on user-prompt phrasing and observing what comes back.

What governs the loop: schema description + model judgement

Since there's no hard logic forcing a particular flow, the schema description is doing real work. The current schema teaches the model:

  • "what did we decide about X" → summary (one call, recap)
  • "find the latest session about Y" → fast (one call, cheap discovery)
  • "I see the fast hit but want the actual back-and-forth" → guided (with anchor from fast)
  • limit defaults to 3; bump to 5–10 when the user wants to be in the retrieval loop
  • Guided synthesis is the most prompt-steerable mode — the main agent shapes it from raw messages, so user-prompt cues like "briefing-style recap" or "include verbatim quotes" land directly. Default lands at analyst-notes feel; explicit shape requests get an executive-briefing feel. See card above for the A/B that established this.

That's the only "loop logic" in the system. Everything else is the model deciding, on each turn, whether to emit a tool call or a text response. If the flow turns out wrong in practice, the fix is iterating on the schema description and re-running the consumer-replay harness (§6.5), not adding code.

Out of scope for this PR; flagged for follow-up

SQLite WAL vs gateway JSONL transcripts

Two transcript stores currently exist: SQLite messages table (canonical, FTS5-indexed, what session_search reads) and per-session JSONL files written by the gateway. PR #21421's session_recall tool chose to read JSONL. Before unifying or building further drill-down on either, understand the requirements: why does the gateway write JSONL? Which workflows depend on JSONL? Could JSONL be derived from SQLite at export time, or vice versa? Worth a focused spec on its own.

PR #21421 disposition

Once mode=guided ships, #21421's session_recall tool overlaps significantly. Decide between (a) close with credit, citing the unified design, (b) leave open for Teknium's call, (c) follow-up that ports JSONL-specific bits worth keeping. Tied to the WAL/JSONL question above.

H2 follow-up (truncation late-content)

Affects summary mode only. The 100K window centres on first match (25/75 bias). When the FTS5 hit is in message 1, late-session work isn't fed to the summariser. Documented in the daily-planning skill. Worth a narrow PR: window-bias balanced around match density rather than first-match anchor.

H3 follow-up (silent FTS5 errors)

search_messages() swallows sqlite3.OperationalError and returns []. If the sanitiser misses an FTS5-special character, the user gets "no matches" with no diagnostic. Surface the error or extend _sanitize_fts5_query. Reproduce first.

Retrieval is the deeper lever (FTS5 ranking + query construction)

The consumer replay (§6.5) showed both modes share the same FTS5 retrieval set — so when retrieval misses (Q1 returned cron transcripts instead of the actual work session; Q4 returned 0 hits), no mode rescues it. The highest-leverage follow-up is improving retrieval itself: (a) auto-OR rewriting for multi-keyword queries (currently default-AND footgun), (b) title and recency-aware ranking on top of FTS5 BM25, (c) potentially a semantic-search complement (embedding store keyed on session id + recent turns) for "what was the design / decision / latest update" question shapes. Bigger than this PR — but worth a dedicated spec, because every mode benefits from better hits.

Steering improvements: wider fast limit + leaner guided payload

Now that guided is reframed as a steering surface (§6), two follow-ups follow naturally:

  • Wider fast hit list. Currently limit=3 by default. Bumping to 5–10 gives the user (and the agent) more anchors to choose from before committing to a drill — directly improves the steering loop's value because "wait, none of these are the right session" is a common case.
  • Strip tool-result bodies from guided payloads. On Q1, 49 kB of the 49 kB guided response was dominated by JSON tool-result content (prior session_search calls inside the cron transcript). For steering purposes the agent just needs to see the shape of the conversation around the anchor — role, tool name, content preview — not full JSON dumps. A truncation pass on tool-role messages would knock the payload back to single-digit kB while preserving the navigational signal.

Both improvements lean into "user in the loop" rather than "tool runs alone faster" — they're follow-ups, not blockers for this PR.

FTS5 default-AND footgun

Q4 returned 0 results because no message contained all three keywords. Schema description already warns ("use OR for broad recall"). Consider auto-OR rewriting for multi-keyword queries that would otherwise miss, with a flag for strict-AND when needed.

Profile harness extensions

More queries, per-individual-summarize-call latency capture (we currently only capture sum-of-walls), test against trigram CJK paths, capture per-session transcript size to correlate with summary latency. The harness is reproducible (see section 10).

9.5. Guided mode results

Guided shipped — measured against the original criteria

This section was originally a holding pattern: "what guided needs to deliver before the default decision is made". Guided is now implemented (commits 4–6 on this branch) and the §6.5 replay re-ran with all three modes. Below: the criteria each case set, and what we actually saw.

Case for fast-as-default — rejected, with caveat

Hypothesis: if guided composes cheaply with fast and covers the synthesis use case, fast-as-default becomes viable.

What we saw: guided's tool-side DB read is 2–3 ms, but that number is misleading in isolation. Guided is never used standalone — it always rides on a prior fast call plus a main-agent inference turn that picks the anchors (~15 s on Opus). The honest end-to-end cost of "fast → guided" as a drill-down workflow is ~15 s, dominated by inference, in the same order of magnitude as summary's 42–66 s tool wall — not below it. Quality-wise, on Q1 the fast→guided answer was more faithful than summary alone (it surfaced the four-pass span-manifest design that summary missed) — that's the real win, not speed.

Verdict: fast-as-default would force every drill-down through that extra inference turn for end-to-end cost roughly equal to summary, and possibly worse since summary's aux model is smaller and faster than the user's main model. Fast stays opt-in; the schema teaches the agent to use it when the user wants to be in the retrieval loop, not when the user wants the fastest path to an answer.

Case for summary-as-default — supported (we kept it)

Hypothesis: summary stays default if guided requires the agent to already know which message to anchor on, defeating the "I don't remember the session" use case.

What we saw: guided always requires fast first to produce a usable match_message_id. That's two tool calls minimum for the discover→drill flow, vs summary's one call. For an agent answering "what did we decide about X" without a clear single-session target, summary is the simpler default — even at 30s tool wall.

Surprise finding — guided's payload is bigger than summary's, and the composed cost is bigger still

We expected guided to be the smallest payload (no auxiliary LLM, just raw messages). Instead it's the largest on long-message sessions: Q1 multi-anchor guided returned 131 kB vs summary's 21 kB. Three windows of 11 messages each, some of which were multi-kB tool outputs.

And that's just the second tool call. The agent had to call fast first to learn the anchors, so the composed payload the calling agent absorbs across both turns is fast (6.6 kB) + guided (131 kB) = ~138 kB on Q1 — vs summary's single 21 kB recap.

Trade-off: summary spends ~66 s of tool wall to produce a smaller, distilled payload in one call. Fast → think → guided spends ~15 s end-to-end (dominated by the agent-inference turn between the two tool calls, not the tool walls themselves) but the calling agent absorbs three full message windows into its context — those tokens cost compute on every subsequent turn. Lesson: tool-side speedup isn't free at the agent-context level, especially when the "cheap" path is two tool calls deep.

Independent of mode default — retrieval improvements

All three modes lose when FTS5 misses the right sessions. Q1 retrieved cron transcripts instead of Yoni's actual work session; Q4 returned 0 hits. Better FTS5 retrieval (auto-OR rewriting, title/recency-aware ranking, semantic complement) is the highest-leverage follow-up — see §9.

Decision recap

Default stays at summary. Commit 3 on this branch remains as-is. The schema description (revised in commit 6) teaches the agent when to reach for fast (discovery + metadata comparison) and when to compose fast→guided (drill into a known hit). Three modes ship; the default reflects the safest one-call answer for an agent that doesn't know the question shape ahead of time.

10. Reproducibility

How a colleague reruns this on their machine

Prerequisites
  • Local hermes-agent checkout with the salvage branch checked out (or current main if this PR has merged)
  • A ~/.hermes/state.db with at least a few sessions on it (the more, the more representative)
  • Python venv at $HOME/.hermes/hermes-agent/venv (or a worktree-local .venv)
  • auxiliary.session_search configured (or "auto" routing to the main chat model)
Steps
# 1. Snapshot the live DB to a scratch path (read-only, doesn't touch live)
sqlite3 ~/.hermes/state.db ".backup '/tmp/profile-state.db'"

# 2. Edit the QUERIES list at the top of profile_session_search.py
#    to match topics that exist in YOUR DB

# 3. Run the latency / size profiling harness
PYTHONPATH=/path/to/hermes-agent \
  /path/to/venv/bin/python \
  /path/to/profile_session_search.py

# 4. Output of step 3:
#    profile-output/<timestamp>-report.md   — human-readable per-query side-by-side
#    profile-output/<timestamp>-raw.json   — full raw responses for both modes

# 5. (Optional) Edit the USER_QUESTIONS dict in replay_session_search_consumer.py
#    so each query has a corresponding user-style phrasing

# 6. Run the consumer-replay harness against the raw.json from step 4
PYTHONPATH=/path/to/hermes-agent \
  /path/to/venv/bin/python \
  /path/to/replay_session_search_consumer.py \
  profile-output/<timestamp>-raw.json

# 7. Output of step 6:
#    profile-output/<timestamp>-replay.md   — per-query 3-way comparison of
#                                                  the agent's next-turn answer
#    profile-output/<timestamp>-replay.json  — raw replay data
Harness pair — what each one measures
  • profile_session_search.py — measures session_search itself: per-mode latency, response bytes, FTS5 hit shape. Foundation for the §4 latency/size table
  • replay_session_search_consumer.py — measures what the user actually sees: replays the calling agent's next turn against the same auxiliary path session_search uses (auxiliary.session_search), feeding the JSON from step 3 as the tool result. Foundation for the §6.5 consumer-simulation table
  • Both are standalone Python; PYTHONPATH-based imports; no installation required
  • Both read-only against the snapshot; never touch the live DB
  • Each query runs once per mode (latency variance is small relative to magnitude of differences); the replay does up to 3 attempts per call to weather transient empty completions and reports the attempts count
  • Wall-clock end-to-end via perf_counter; profile_session_search.py additionally per-stage instruments via temporary monkey-patches that unwind in finally
  • Both use whatever auxiliary.session_search resolves to in the live config — consume real LLM tokens
